## 2026-08-15 审计更正

`2758af7` 的交付报告曾把 `7fd98b14` 写成“标准经济舱冻结邮件”的复放哈希。该表述不准确。

审计结果如下:

1. `4a98816` 到 `2758af7` 之间只有 `2758af7` 一个提交。该提交修改的是无主方案/无匹配通知分支, 没有重生成标准经济舱冻结基线。
2. `7fd98b14d2cd851925a178c416baf9eb7afbb1c4b17fd91f24dab365e230bf27` 来自活体输入 `data/payloads/79.json`, 对应邮件正文 `44609` 字节, 不是冻结输入。
3. 用 `data/payloads/79.json` 分别调用改动前后的渲染器, 两边确实都得到 `7fd98b14...`; 这只能证明该活体样本在该次改动中零漂移, 不能证明冻结基线零漂移。
4. 用真正的冻结输入 `after_copy_provenance_shanghai_osaka.json` 在 `2758af7` 复放, 仍得到 `d3350c1b...`, 与 `4a98816` 报告一致。

更正后的结论是: 冻结基线没有从 `d3350c1b` 变为 `7fd98b14`; `2758af7` 前后本地人工基线均为 `d3350c1b...`。变化发生在报告所引用的样本身份, 不是邮件输出。

## 基线更替纪律

1. 零漂移比较必须固定同一渲染入口、同一输入夹具、同一输出载体和同一字节编码。快照 JSON 必须把其 `payload` 字段传给 `render_email`, 不得传外层封装或复用快照内嵌的旧 `html` 字段。
2. `data/payloads/*.json` 等活体样本不得静默替代冻结夹具。
3. 有意重冻结必须显式宣告旧哈希、新哈希、原因、日期、输入夹具、生效提交和批准记录。
4. 未找到冻结夹具或无法复放时, 只能报告“冻结验证缺失”, 不得报告“零漂移”。
5. 报告可同时列出活体样本复放结果, 但必须明确标为“活体样本”, 不得使用“冻结基线”称谓。
6. 若代码变更预期不影响邮件, 应先验证当前冻结哈希不变; 若预期影响邮件, 应先解释字段级差异, 再按本节登记重冻结。
7. 受版本控制夹具必须通过 PII 与令牌占位检查; 本地原始夹具只作人工复放, 不得提交。
