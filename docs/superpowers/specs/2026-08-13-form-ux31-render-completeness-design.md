# UX 3.1 渲染完整性契约设计

## 问题定谳

UX 3.0 已保证完整页具名控件不重复，但只检查 `count > 1`，没有检查规范控件 `count == 0`。实测中通知渠道与会议时间已经存在，却埋在长页深处；`buffer_hours` 与 `transport_mode` 则确实没有表单入口。两页互链只位于页底，也让快速创建与完整设置在首屏看起来像单一模式。

## 边界

本轮只修改表单结构、提交回读和测试契约。订阅既有 schema、规范化语义、分析、金额、排序、采集和通知邮件渲染均不改。`buffer_hours`、`transport_mode` 是分析层与规范化层已经支持的可选字段；空值不写入订阅，旧七场景输出不增加字段。

## 渲染宪法

`form_concepts.CONCEPTS` 中每个概念必须声明 `canonical_input_names`。完整页渲染后，每个规范 name 必须恰好出现一次：缺席与重复都会使测试失败。快速页以 `QUICK_CANONICAL_INPUT_NAMES` 声明自己的完整输入集合，并执行同一条 `count == 1` 规则。

条件控件仍在 DOM 中，显隐不影响完整性计数。允许的显隐契约仍仅有：

- 老人/儿童画像补充。
- 邮件地址随通知方式显示。

会议字段不新增 JavaScript 显隐。

## 页面补齐

### 快速创建

标题固定为“快速创建监控”。页头直接显示“需要完整控制？进入完整设置”链接，不再要求用户滚到页底才发现第二种深度。

### 完整设置

标题固定为“完整设置”，页头直接显示“返回快速创建”。“什么时候”中新增静态“当天往返与会议参数”小节，说明“仅当天往返行程需要，其余可留空”，完整呈现当天往返、会议起止、缓冲、交通方式、车程和冗余。

“怎么提醒”保留邮件、PushPlus、两者三态和邮箱条件输入；编辑存量订阅从 `notification_goals` 回填。

## 端到端合同

本地 Edge smoke 必须完成：页1到页2再返回页1、页2选择 email 并填写邮箱、勾选当天往返并填写会议时间、提交后在确认页看到邮箱和会议值。任一 console error 仍然失败。

八场景夹具新增“当天往返会议完整参数”，旧七场景逐字段必须保持不变。
