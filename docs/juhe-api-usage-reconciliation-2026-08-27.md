# Juhe 配额台账与控制台对账

## 1. 结论

2026-08-01 至 2026-08-26，聚合数据控制台合计 **219** 次，
`data/api_usage.json` 合计 **202** 次，控制台比本地多 **17** 次。

17 次差异已逐日、逐轮闭合：六个篮子轮在已经开始 Juhe 请求后被中断，
但没有运行到轮末的 `[API统计]`、`[配额台账]` 和 `[轮档结束]`。修复前实现只在
`print_request_cache_stats()` 的轮末路径把整轮 `actual_by_source` 批量写入
`api_usage.json`，因此这些已被供应商计费的请求整轮漏账。

这是确定的台账持久性缺陷，不是缓存命中误计、失败重试多计、跨日边界错位，
也不是同一轮重复写入。2026-08-27 已改为每次源调用结束立即持久化，轮末只汇总
并校验恒等式。8 月少记的 17 次保持历史原状，不手工回填。

`[juhe] request params` 紧邻 `requests.get()` 之前；`[juhe raw] status_code`

## 5. 替代原因核对

### 5.1 失败重试

失败重试会作为第二次物理请求进入 `actual`。08-24 的订阅轮
`collection_20260824T135737160437` 中，返程首次请求 `ReadTimeout`，随后重试成功；
该轮 Juhe 本地计数为 3（去程 1 + 返程首次 1 + 重试 1）。控制台当日总数与
“本地 5 + 另一个中断篮子请求 1”一致，说明该重试没有制造差异。

此前的 `PermissionError` 发生在 HTTP 响应之后的本地缓存写入阶段；若触发源级
重试，第二次同样是物理 HTTP 请求。把这类重试计入额度符合供应商实际扣次口径。

### 5.2 缓存命中与面板复用

请求缓存、持久缓存、面板复用、源级跳过都在 `_record_actual()` 之前返回；
`api_usage.json` 写入取的是 `by_source.actual`，不取 `requested`、`hits` 或
`panel_reused`。本区间可见的 Juhe `[API调用]` 均伴随
`[juhe] request params`，未发现源内 15 分钟缓存返回却被记为实际请求的样本。

结构上仍有一个待单独防御的风险：外层 `force_fresh` 绕过请求缓存，但
`JuheSource.fetch()` 仍有自己的 15 分钟缓存。虽然本区间没有触发，未来应让“实际
供应商请求”在 HTTP 边界记账，而不是在源适配器调用边界记账。

### 5.3 跨日边界

本区间 41 条含 Juhe 的台账 entry 均记录于 `09:01:22+08:00` 至
`22:35:45+08:00`，没有 23 点或 0 点附近的轮次。控制台与本地除六个中断日外
逐日一致，因此本次差异不是 UTC/Asia/Shanghai 跨日归属造成。

现行 `record_actual_requests()` 默认使用 `date.today()` 作为日键，长期仍应改为
项目统一的 Asia/Shanghai 时钟；这属于日期语义防御，不是本次 17 次缺口的根因。

### 5.4 篮子与订阅轮重复计数

本区间有 Juhe 计数的 41 条 entry 中，`round_id` 无重复。多个轮次同日运行时，
控制台数字等于各轮真实请求之和；这是多次物理调用的真实成本，不是同一 entry
被重复写入。跨轮同键重复采集属于调用策略问题，不能从配额台账中去重掉。

## 6. “约 19 次”历史差额

本次控制台日明细能够严格证明 08-01 至 08-26 少记 **17** 次。向前查看现有
`data/basket.log`，还发现 `basket_20260727T144129` 有 1 个 Juhe 请求标记，
无响应、无轮末统计、无台账 entry，与本次六个中断轮同型。因此 07-27 至 08-26
可确认至少少记 **18** 次。

剩余约 1 次不能用现存证据精确归因：07-22 的本地台账只有聚合数，没有 v2
`entries` 逐笔 lineage；当时轮档也尚未完整覆盖。不能把“约 19”强行改写为
19 个已定位事件。结论应表述为：**17 次在本次控制台窗口内逐日闭合，另 1 次有
同型日志证据，尾差约 1 次受旧台账证据缺口限制。**

## 7. 修复落地与边界

### 7.1 持久化时机

每次进入 `request_cache` 的实际源调用分支后，在该次 `source.fetch()` 结束的
`finally` 中立即调用 `record_actual_requests({source: 1})`。首次调用与每次重试
分别形成 entry；缓存命中、面板复用、源级前置跳过和熔断分支不会进入该边界。
轮末不再增加计数，只按 `round_id` 汇总 entry，并打印 `[配额恒等式]` 对比内存
`actual` 与已落账次数。

硬终止发生在 HTTP 尚未返回时，返回后记账无法证明该笔是否已被供应商扣次；但该轮
此前已经结束的调用均已持久化。轮档中的 `[API调用]` 与 `collection_cells` 的
`interrupted` 状态只作对账旁路，不自动补写台账，避免把发送前日志误当成已扣次事实。

### 7.2 性能与锁竞争

离线临时文件基准中，26 次逐笔原子写的中位耗时约 264 ms（约 10.17 ms/笔）；
同样 26 次一次批量写约 3.64 ms。当前每轮只有 6 至 26 次请求，且同机采集受
single-flight 约束，约四分之一秒的最坏常见增量远小于网络耗时。此规模不采用
“批量缓冲+超时刷盘”：缓冲窗口会重新制造进程中断漏账。若未来调用量或台账文件
显著增长，应改为独立 append-only attempt 存储，而不是恢复内存缓冲。

### 7.3 与 `collection_cells` 的关系

两套记录不能互相派生。`collection_cells` 按 `(round_id, request_fingerprint)` 唯一，
描述一个逻辑请求的 planned→final 状态；同一请求的 OSError 重试会折叠在同一个
cell。`api_usage` 描述供应商计费口径下的物理尝试，重试必须另计。前者用于数据质量、
lineage 与中断状态，后者用于配额；二者仅在轮末交叉核对。

### 7.4 历史处理

2026-08-01 至 2026-08-26 的 17 次少记保持不变，不手工补写 `dates` 或 `entries`。
文档中的控制台差值就是已知偏差来源；后续新轮从即时记账启用时点开始形成完整序列。
Juhe 源内 15 分钟缓存与 Asia/Shanghai 日界归属仍按第 5 节作为独立防御项保留。
